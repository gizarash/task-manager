# task-manager

## Этап 1: CLI Task Manager

### Задание

Напиши консольную программу управления задачами. Программа должна поддерживать следующие команды:

```
go run main.go add "Купить молоко"
go run main.go list
go run main.go done 1
go run main.go delete 1
```

### Требования

add <текст> — добавляет новую задачу  
list — выводит все задачи с ID, статусом и текстом, например:
```
[1] [ ] Купить молоко
[2] [x] Позвонить маме
```
done \<id> — отмечает задачу как выполненную  
delete \<id> — удаляет задачу

Если команда неизвестна или аргументы неверны — вывести понятное сообщение об ошибке.

### Ограничения этапа

* Хранение только в памяти (данные не сохраняются между запусками — это будет этап 2)
* Всё в одном файле main.go
* Не использовать сторонние библиотеки

### На что обратить внимание

* Как ты определишь структуру задачи?
* Как будешь хранить список задач?
* Как будешь разбирать аргументы командной строки?

Теперь данные должны сохраняться между запусками. Команды остаются теми же, но теперь:

### Задание

### Логика работы:

1. При старте — читать задачи из файла (если файл не существует — начинать с пустого списка)

* Использовать только стандартную библиотеку: encoding/json, os

## Этап 4: Graceful Shutdown + Background Worker

Добавим две вещи, которые встречаются в любом реальном Go-сервере:

1. **Graceful shutdown** — сервер при получении SIGINT/SIGTERM (Ctrl+C) должен:

* перестать принимать новые запросы
* дождаться завершения текущих запросов
* корректно завершиться

2. **Background worker** — горутина, которая каждые 30 секунд пишет в лог статистику: сколько задач всего и сколько выполнено.

### Что нужно изучить/использовать:

* os/signal + signal.NotifyContext
* http.Server (вместо http.ListenAndServe)
* server.Shutdown(ctx)
* goroutine + time.Ticker
* context.Context для остановки воркера

### Требования

* Воркер должен останавливаться вместе с сервером (не висеть после shutdown)
* Изменения только в cmd/api/main.go

## Этап 7: HTTP Middleware

Каждый production-сервис логирует входящие запросы: метод, путь, статус ответа, время выполнения. В Go это делается через middleware — функцию, которая оборачивает `http.Handler`.

### Задача:

Написать middleware `LoggingMiddleware` и подключить его к серверу.

### Требования:

1. Функция с сигнатурой:
```
func LoggingMiddleware(next http.Handler) http.Handler
```
2. Для каждого запроса логирует через `slog`:
* метод (`GET`, `POST`, ...)
* путь (`/tasks`, `/tasks/1/done`, ...)
* статус ответа (`200`, `404`, ...)
* длительность обработки (в миллисекундах)

3. Middleware подключается в `cmd/api/main.go` — оборачивает весь `mux`

4. Никаких сторонних библиотек

### Подсказка о проблеме:

`http.ResponseWriter` не предоставляет метода для чтения статус-кода после того, как он был записан. Тебе понадобится собственная структура, которая реализует `http.ResponseWriter` и дополнительно запоминает код.

### Где размещать код:

Middleware можно положить в новый файл `cmd/api/middleware.go` (рядом с `main.go`).

## Этап 9: Конфигурация через переменные окружения

Сейчас порт и путь к БД захардкожены в `main.go`:
```
store.New("store.db")
Addr: ":8080"
```
В реальных приложениях конфигурация передаётся извне — через env vars или флаги запуска.

### Задача:

Вынести конфигурацию в отдельную структуру и читать её из переменных окружения.

### Требования:

1. Новый файл cmd/api/config.go со структурой:
```
type Config struct {
    Port   string
    DBPath string
}
```

2. Функция `NewConfig() Config` — читает значения из env vars:
* `APP_PORT` → `Config.Port` (default: `"8080"`)
* `APP_DB_PATH` → `Config.DBPath` (default: `"store.db"`)

3. `main.go` использует `cfg := NewConfig()` вместо хардкода

4. Никаких сторонних библиотек — только `os.Getenv`

### Подсказки:

Для чтения env var с fallback на дефолтное значение удобно написать маленькую вспомогательную функцию внутри `config.go`:

```
func getEnv(key, defaultValue string) string { ... }
```
